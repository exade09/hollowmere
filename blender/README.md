# Blender sources

Both rooms are procedural: the `.blend` files are under 600 KB because every
block of masonry, every torch and every flagstone is generated by script. That
means the scenes can be edited by changing a number and rebuilding in seconds,
and the repository stays small.

Built with Blender 5.2, EEVEE, 1920×1080, 24 fps.

## Files

| File | What it does |
| --- | --- |
| `hollowmere_sanctum.blend` | the tower room; 748 objects |
| `hollowmere_undercroft.blend` | the crypt below; 855 objects |
| `build_undercroft.py` | rebuilds the crypt from scratch, including its outlines and the mascot |
| `build_outlines.py` | rebuilds the teal interaction outlines in the Sanctum |
| `finalize_outlines.py` | the fresnel rim on materials plus the outline pulse |
| `render_clips.py` | renders the Sanctum's nine clips |
| `render_clips_uc.py` | renders the crypt's four clips |
| `render_states.py` | renders the Sanctum's eight hover frames as stills |
| `export_hotzones.py` | prints the SVG hotzone rectangles used by `lib/scenes.ts` |
| `render_ui.py` | the widget furniture: one low-poly portrait per object plus the faceted stone slab behind every panel |

## Rebuilding

```bash
# the crypt, from scratch
blender -b --factory-startup --python build_undercroft.py

# clips: 9 for the Sanctum, 4 for the crypt
blender -b hollowmere_sanctum.blend   --python render_clips.py    -- <outdir>
blender -b hollowmere_undercroft.blend --python render_clips_uc.py -- <outdir>

# hotzone rectangles for the site
blender -b hollowmere_sanctum.blend    --python export_hotzones.py -- sanctum
blender -b hollowmere_undercroft.blend --python export_hotzones.py -- undercroft

# widget icons and the panel slab, straight into the site
blender -b hollowmere_sanctum.blend    --python render_ui.py -- sanctum    ../public/ui
blender -b hollowmere_undercroft.blend --python render_ui.py -- undercroft ../public/ui
```

`render_ui.py` isolates one group of objects at a time, drops the room's own
lights for a shared three-point rig, and renders on transparency, so the icons
keep the exact materials of the objects they portray and still read as one set.
Two per-icon overrides exist because a single rig cannot serve everything: the
parchment map is almost white and needs the exposure pulled down, and it hangs
on the 288-degree panel, so it is viewed along its own normal instead of the
shared three-quarter direction.

Each render script takes an optional clip name as the second argument and the
literal `test` as the third, which renders three sample frames instead of the
whole loop — useful for checking a pose without waiting on 96 frames.

Encoding to mp4 afterwards:

```bash
ffmpeg -framerate 24 -i "<outdir>/<clip>/f_%04d.png" \
  -c:v libx264 -preset slow -crf 20 -pix_fmt yuv420p -movflags +faststart -an \
  <clip>.mp4
```

## Two traps worth remembering

**The crypt is mirrored on X after it is built.** The camera looks down −Y, so
screen-right is world −X, and the layout came out backwards on the first pass.
The fix is a mirror at the end of `build_undercroft.py`, which flips every mesh
normal. Anything added *after* that step therefore has to account for a negative
matrix determinant — the outline hulls inflate along `−normal` and skip the
face flip, or they end up either invisible or solid.

**Shadows.** With seventeen lights, EEVEE's shadow atlas overflows at 1080p
("Shadow buffer full") and Blender silently drops shadows at random, which makes
the brightness flicker frame to frame. `shadow_maximum_resolution = 0.012`
on every light keeps it inside the pool. If a render starts shimmering, check
the log for that message first.
